## Claude Code's review (real run, 2026-11-03, verbatim; line numbers refer to the d-09 files)

I read the full `git diff d-07..d-09 -- apps/web`, guides 04 and 05 under `apps/web/node_modules/remix/guides`, the agent's `/agents/*` gate (`apps/agent/src/index.ts`) and the close handling in `agents`' `WebSocketChatTransport`. I didn't edit any files or run anything. I found 6 issues, most important first, plus nothing to fix under security.

### 1. The protocol logic lives inside the component
**`apps/web/app/actions/public/chat.tsx:25-92`**
- `Chat` builds the `AgentClient`, parses raw socket frames, routes four `MessageType`s into the transport, and writes the tool-approval message format by hand (`:85`). It also owns the message list and the rule that ignores server updates while `busy` (`:38`).
- Guide 05 ("Keep application logic outside components") says to keep UI state in the component and put data and operations in plain TypeScript, using its `CartModel extends TypedEventTarget` example.
- **Why it matters:** none of this can be tested without a DOM. The next lesson that touches the protocol will have to edit a 130-line component. Also, `JSON.parse` at `:31` will throw inside the listener on any frame that isn't JSON.
- **Smallest fix:** move lines 25-92 into `app/actions/public/chat-session.ts` as `class ChatSession extends TypedEventTarget<{ change: Event }>`, with `messages`, `busy`, `offline`, `send(text)` and `answer(id, approved)`. In the component, do `session.addEventListener('change', () => handle.update(), { signal: handle.signal })`.

### 2. "Sending your answer…" can stay on screen forever
**`chat.tsx:20, 83, 94-96`**
- `answering.add(toolCallId)` is never removed. If `exchange` fails, the card loses its buttons and keeps saying "Sending your answer…" with no way to retry.
- The same happens if `reconnectToStream` returns `null` (`exchange` skips `show` without saying anything), or if the server's update arrives while `busy` (dropped at `:38`).
- **Why it matters:** the screen claims something is in progress when it isn't. That's exactly what the comment at `:57` says is worse than an error.
- **Smallest fix:** in `answer`, use `return exchange(...).finally(() => { answering.delete(part.toolCallId); handle.update(); })`. In `exchange`, when `stream` is null, set `problem`.

### 3. A failed send looks delivered, and the typed text is lost
**`chat.tsx:74` and `apps/web/app/ui/prompt-input.tsx:17`**
- The user's message is added to the list before sending, and stays there if the send throws.
- `PromptInput` clears the box before calling `onSend`, so the text is gone.
- The error at `:65` ("Klippy couldn't answer") suggests the message arrived. After a reload it may not be there.
- **Smallest fix:** in `send`, save `const before = messages`, and on failure restore it and say "Your message wasn't sent." Have `onSend` return `Promise<boolean>`, and only clear `box.value` when it resolves `true`.

### 4. Lost connections aren't announced, and Send stays enabled while offline
**`chat.tsx:116, 129`**
- "Reconnecting to Klippy…" is inserted with no live region, so screen-reader users never hear it.
- `PromptInput` already has a `disabled` prop (`prompt-input.tsx:5, 28, 37`), but `Chat` never passes it. You can type and send into a closed socket.
- **Smallest fix:** add `role="status"` to the notice, and use `<PromptInput busy={busy} disabled={offline} onSend={send} />`.

### 5. Accessibility details
- **`chat.tsx:55, 122`:** `announced` only changes when the text changes. Two identical replies in a row (for example "Done.") are only read once. Fix: clear `announced` at the start of `exchange`.
- **`chat.tsx:104`:** the button just says "Deny", so in a screen reader's list of buttons it says nothing about what is being denied. Fix: `Deny {what}`.
- **`apps/web/app/ui/tool.tsx:29-31`:** `aria-label` on a `<pre>` (which has no role) is ignored by most screen readers, so "Input", "Result" and "Error" are never read. Fix: put a visible `<p class="muted">Input</p>` before each `<pre>`.
- **`prompt-input.tsx:21`:** uses `<label for=...>`, but guide 04:211 shows `htmlFor`. It matches `notes-page.tsx:20` and type-checks, so I'm just noting it.

### 6. Remix patterns: `entry.ts` drops the guide's guard, and the island URL is hard-coded
- **`apps/web/app/actions/public/entry.ts:7-10`:** guide 05's `loadModule` throws ``Unknown component: ${url}#${name}`` when the export isn't a function. Without that check, a renamed export fails later with a vague error. Fix: add the 3-line check.
- **`chat.tsx:14`:** `clientEntry('/assets/chat.js#Chat', …)` ties the island to the esbuild `--outdir` and entry name in `package.json:10`, whereas the guide uses `import.meta.url`. Fix: a comment at both places saying they must change together.
- The rest matches guides 04 and 05:
  - `queueTask` for browser-only setup (the `typeof window` check at `:26` is redundant but harmless).
  - `handle.signal` closes the socket.
  - Messages have keys.
  - Props are serializable.
  - Read-once `initial` follows the guide's `initialCount` pattern.

### Security: none
I checked each of these:
- **Origin:** `controller.tsx:28` requires an exact `Origin` match, and a missing `Origin` is rejected.
- **Login:** `requireUser` protects `/chat`.
- **Cookie:** removed before forwarding (`:32`).
- **Token:** added only on the server in `agent.ts`, and the agent re-checks it (`apps/agent/src/index.ts:21`).
- **Agent guards:** the agent keeps its rate limit and its 2,000-character input cap on chat (`apps/agent/src/agent.ts:25-28`).
- **Links from model output:** source hrefs are limited to `^https?://` (`message.tsx:39`) and use `rel="noreferrer noopener"`.
- **Rendering:** model text, tool input and tool output are shown as text, never as HTML.
